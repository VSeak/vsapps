# Sit Start

A personal site for a bouldering coach. Coaches sign in to manage students and write their training plans. Each student signs in to see only their own plans and leave notes on sessions.

## How it's built

- One page (`index.html`: the header and page shell), styled by `styles.css`, run by plain JavaScript in `js/`. No build step. supabase-js comes from jsDelivr pinned to an exact version (bump it on purpose, then test sign-in), fonts from Google Fonts. Pages fetch in parallel: a query that needs another's ids filters through a join instead (`planNotes`, `homeNeeds`), so a page waits for one round trip.
- The JS files are classic `<script>` tags, not modules: they share one global scope, so any file can call any other's functions. They load in the order listed in `index.html`, and `boot()` runs after the last one. Code that runs straight away at load (not inside a function) can only use what earlier files define. Don't declare the same top-level name in two files (a duplicate `const`/`let` stops the second file loading). A new file needs its own `<script>` tag. Never put CSS or JS back inline in `index.html`: styles go in `styles.css`, code in the `js/` file that fits the list below (or a new file if nothing fits).
  - `core.js`: `CONFIG`, page state (`me`, `draft`, `dirty`), helpers (`esc`, `flash`, `ask`, `crumbs`, field errors), `markRequired` (a small red * after every required field's label, and on `fieldset[data-required]` legends; the user asked), pronouns, date formats, `sendLink`.
  - `app.js`: `boot`, `loadMe`, `route`, the leave check and unsaved marks, foldable cards, the unsaved bar, sign-in pages, staff Home (`ADMIN_PAGES`).
  - `users.js`: the Users page and `#/user/<id>` (roles, staff access).
  - `students.js`: the Students list.
  - `cards.js`: shared cards and pieces: coaches, pagers, the Next Session card and Session History, Coaching Status, Goals, Coach Notes.
  - `student-page.js`: `#/student/<id>` (`adminStudent`).
  - `exercises.js`: Exercises & Drills (the master list), the `#exMenu` name picker and the exercise browser (`#exSheet`, `#exPanel`).
  - `drag.js`: `dragSort`, drag to reorder (used by the plan editor).
  - `plan-editor.js`: `#/plan/<id>` for staff (`adminPlan`, `savePlan`).
  - `student-view.js`: plans as students see them, the student home.
  - `training-log.js`: the Training Log: `LOG_FIELDS`, summaries (`logSummary`), the Log sheet (`#logSheet`), the History sheet (`#logHist`), the student's home card and the coach's student-page card.
  - `notes.js`: plan notes, shared by the student view and the plan editor.
  - `coaching-session.js`: the Coaching Session card on `#/student/<id>` (`bindCoachSession`, `renderCoachSession`) and Coach View (`#csView`).
  - `messages.js`: Messages (texting between a student and their coach): the header button and unread counts, a thread (`msgThread`), the coach's inbox (`adminMessages`), live updates and push notifications. `sw.js` (beside `index.html`) is its service worker.
- Backend: Supabase (auth + Postgres). `supabase/schema.sql` creates everything. Setup steps are in `SETUP.md`. `CONFIG` at the top of `js/core.js` holds the project URL and publishable key.
- **Security is in the database, not the page.** Row-level security in `schema.sql` decides what each user can read or write. Any new table needs RLS and policies. The page never holds the secret key.
- Serve it over http (`npx serve .`), since sign-in links need a real address.

## Accounts

- Staff = a row in `public.staff` (matched by the signed-in email) with `roles`, a set of separate roles: `coach` (students, plans, goals, notes) and `admin` (the Users page: every user, staff and students). One person can have both. `my_roles()` returns them; RLS uses `is_coach()` and `is_admin()`. Admins can edit students' rows (details, invites) but not plans or goals. The `keep_an_admin` trigger refuses any change that leaves no admin, and the page won't let you remove your own Admin role. One staff member is the **owner** (`staff.owner`, set only in the SQL Editor): the `protect_owner` trigger stops anyone else changing their roles or email or removing them, and the owner always keeps Admin. The page locks their roles and hides Remove Access for other admins. To add a role: allow it in the `staff.roles` check, then add it to `ROLE_LABEL`, `ROLE_PLURAL`, `ROLE_HINT` and `STAFF_ROLES`.
- **Coach ownership:** every coach reads every student, but only a student's current coach changes them: plans, sessions, goals, details, next session, coaching status, invite, and replies to their plan notes (`can_coach(student)`, plus `can_coach_plan` / `can_coach_session`, in the RLS policies). A student with no coach can be changed by any coach. Other coaches get a read-only student page (an alert says who coaches them) and a read-only plan, but can add Coach Notes (editing only their own; the student's coach edits any) and add past sessions (only the coach or an admin deletes them). The page mirrors this with `canCoach(s)`. The Students list has My Students, No Coach (only when there are some), Other Coaches' Students (with "Coached by", names from `coach_list()`, since coaches can't read other staff rows) and Inactive; warn tags and Latest Student Notes cover only students you can change. The home tile counts your own active students. `check_student_coach` also fires on `training_ended_at`: End Coaching sets the coach to none (and stamps the server time), and Resume Coaching gives the student back only to the coach they had when it ended, if that coach is the one resuming; anyone else leaves them with no coach for an admin to pick. Otherwise End then Resume would let a coach take a No Coach or another coach's inactive student (`endedCoach()` mirrors it for the hint).
- **Staff who are also students:** a staff member gets a student row with the same email (the Student checkbox under Roles in Add User's Staff mode and on a staff member's `#/user/<id>`; once ticked it stays ticked with a link to the student record, and removing it is Delete Student on that record). `loadMe` always runs `claim_student()`, so `me.student` is set for them too, and the home page gets a **View My Training** tile (`#/me`, the student home under a "My Training" heading, without Your Pronouns). `route()` sends their own `#/student/<id>` to `#/me` and `adminPlan` shows their own plan as the student sees it (`isSelf`). Nobody can be their own coach (`check_student_coach`; the coach picker leaves them out), `is_self()` keeps Coach Notes about themselves hidden from them, and plan notes they post on their own plan are student notes (`notesCtx.coach` decides `from_coach`, not the role). Changing the staff email in the invite form changes the student email too.
- Staff are added on the Users page (the Add User dialog in Staff mode sends the invite straight away). Typing an email another app knows (`staff_lookup`, admins only, which asks `person_in_other_app()`: empty here, replaced by Top Out's schema to read `team_staff`) fills in any empty name and pronoun fields (`watchLookup`, `setPronouns`); if that login already has a password, there is no invite (the button reads + Add Staff) and `invited_at` is stamped anyway, so they just sign in (the user asked for no password change). Its Staff / Student switch (`#addKind`) lets an admin add a student too: Student mode hides and disables the email and roles and inserts just a `students` row (name, pronouns). A coach adder becomes their coach (`check_student_coach`) and goes to `#/student/<id>`; an admin-only adder goes to `#/user/<id>` to pick the coach. The invite still waits for a plan and a goal. Staff who leave are **deactivated**, not deleted: the Staff Access card on `#/user/<id>` (hidden on your own page and the owner's) has Deactivate, which sets `staff.deactivated_at`. They keep their row, login and history. `my_roles()`, `is_coach()` and `is_admin()` ignore them, and the `staff_deactivated` trigger deletes their `auth.sessions` (unless the login is also a student's). Their password still works on purpose: `loadMe` spots a deactivated staff row after sign-in, signs them out everywhere, and the sign-in page shows an "Account Deactivated" popup (`deactivatedNotice`; `ask()` with `cancel: false`). Only after a valid password, so guessing an email never reveals the account (a Supabase ban was rejected for that reason: it answers before checking the password). `gate_signup` refuses a deactivated staff email with no login yet. The trigger also leaves their students with no coach and refuses deactivating yourself; `protect_owner` refuses deactivating the owner; `keep_an_admin` counts active admins only. Reactivate clears it (students don't come back). The Users list tags them Deactivated, sorts them last, and has a Deactivated Staff filter (the role filters leave them out). Inactive students (coaching ended) get the same treatment: an Inactive tag, sorted last (before deactivated staff), and an Inactive Students filter; `adminUsers` reads `training_ended_at` from `students`, since `list_users()` doesn't return it. Only a deactivated staff member has Delete Staff: `delete_staff()` (which refuses anyone still active) removes the row and their login (kept if they are also a student). Staff invites pass `staff: true` in the login's data, and both emails switch to staff wording with `{{ if .Data.staff }}`. Staff emails sign off "Welcome aboard!" (invite) or "Thanks for being on the team!" (sign-in link) instead of "Happy training!". Both emails are signed with the first name of the coach or admin who sent them (`{{ .Data.sent_by }}`, or "Sit Start" if it is missing): `sendLink` passes it as data for a new login and first calls `stamp_sender()`, which writes the caller's own staff first name onto an existing login, since Supabase ignores data for a login that already exists.
- Students are added by name first (`email` and `invited_at` start empty), so the coach can build their plan before inviting. The Account card on the student page saves the email, calls `signInWithOtp` to email a link, then sets `invited_at`. The invite waits until the student has a saved plan (one with a title) and a goal: `gateInvite()` disables the button and says what is missing. The student page checks its own data (and re-checks as goals change); the Users page asks `student_ready()`, since admins can't read plans or goals. Until the invite goes out, the Account card (`accountCardStart`, on both `#/student/<id>` and `#/user/<id>`) is the warn color with a Not Invited tag and a warn box. Once a student has signed in, an admin changes their email with Change Email on `#/user/<id>` (an `ask()` dialog), through `change_student_email()`, which also changes their login's email at once (and refuses one a staff member or another login has). The OLD address gets a notice (never the new one), saying to contact their coach or an admin if it's a mistake. It goes out first, while the old address still has a login: `prepare_email_change()` checks the new email and stamps `email_changed_to` (and `sent_by`) on the login and returns the old email, the page sends it the Magic Link email (its `{{ if .Data.email_changed_to }}` wording, no sign-in button), and only then changes the email. If the notice doesn't send, nothing changes. `stamp_sender()` clears `email_changed_to` before any normal link. Before they sign in, the invite form changes it. The list shows Not Invited, Invited or Active. The `gate_signup` trigger on `auth.users` refuses any sign-up whose email isn't in `students` or `staff`, so sign-ups can stay enabled.
- **Delete Student** is on the Coaching Status card of an inactive student (End Coaching is the archive; delete is for someone added by mistake) and of a student who was never invited (no `invited_at`, no `user_id`; the user asked, migration `2026-10-10-delete-uninvited-student.sql`); `delete_student()` refuses anyone else still being coached. It removes the row and the matching `auth.users` login (never a staff member's). Without that, re-adding the email would find the old login: Supabase sends the Magic Link email instead of Confirm signup, and the old password stays.
- Invites go through `sendInvite()`: if the login already has a password (`login_has_password()`, e.g. a Top Out coach who becomes a student or staff here), no email is sent, `invited_at` is still stamped and the flash says they can sign in now (the user asked for no password change). Names and pronouns are shared with Top Out: `person_pull` / `person_push` triggers (defined in Top Out's schema) keep `staff`, `students` and `team_staff` rows with the same email in step.
- Staff send sign-in links (the invite, or Send Sign-In Link). Anyone can also tap **Forgot Password?** on the sign-in page (`forgotPassword`): an `ask()` dialog takes the email and calls `resetPasswordForEmail`, which sends the Reset Password email (`supabase/emails/reset-password.html`, signed "Sit Start") and leads to "Choose a Password" through `PASSWORD_RECOVERY` / `?setpw=1`. Supabase sends nothing for an email with no login but answers the same way, and the page always says "If … has an account, a link is on its way", so it never reveals whether an email has an account (the same reason as the deactivated-staff check). A deactivated staff member who resets still gets the Account Deactivated popup after the link.
- Links go through `mailer`, a second client with no stored session, so sending one never touches the coach's session. Both clients use the implicit flow, so a link works on any device.
- Links redirect to `CONFIG.siteUrl` (the live site, so links sent from localhost still work on a phone), or the current address if it is empty, plus `?setpw=1`. After sign-in, `claim_student()` links the account to the student row (`students.user_id`). A student without `user_metadata.password_set` is sent to "Choose a Password".

## Data

- `staff(id, email, first_name, last_name, name, pronouns, roles, invited_at, owner, deactivated_at)`: `roles` is a text array (`{admin,coach}`, at least one). Admins can read every row; other staff only their own (for the home page greeting). The Users page reads everyone through `list_users()`, which adds `last_sign_in_at` from `auth.users` for the Active status, `owner` and `deactivated_at`.
- `students(id, first_name, last_name, name, pronouns, email, invited_at, user_id, coach_id)`: `name` is generated from first + last (read it for display; write the two parts). First and last are separate so a first name with a space greets correctly. `email` is null until the coach adds it. `coach_id` is their current coach (a staff member with the Coach role, or none). `next_date`, `next_start`, `next_end`, `next_location` are their next training session: all four set (end after start) or all null (`next_session_whole` check). Coaches and admins set it in the Next Session part of the Sessions card on `#/student/<id>` and `#/user/<id>` (`sessionsCardHTML`, `bindSessions`); students can only read their own row, so they just see it at the top of their home page (`nextSessionAlert`) until it ends (date + end time, `nextPassed`). The page keeps the date to today or later. **Several sessions ahead** (another coach asked; migration `2026-10-10-upcoming-sessions.sql`): `upcoming_sessions(id, student_id, session_date, start_time, end_time, location)` holds the ones scheduled after the Next Session, which stays on the student's row (so everything that reads `next_*` still works). Staff read them, the student's coach or an admin changes them, the student reads their own. The Next Session is the earliest that hasn't ended: `applySchedule(s, ups)` (cards.js) works that out on the row on every page that shows it (`s.later` the ones after it, `s.ended` ended ones not in the history yet, which `historyOf` counts as past), so students and other coaches see it rolled forward at once, and `settle_sessions(student, local now)` saves it (the ended ones to Session History, the earliest left as `next_*`) when their coach or an admin opens the student (`settleSessions`) and after every change. When all have ended, the last one stays as the ended Next Session, as before, so Needs Update only shows when nothing is left. The dark card lists them under **Upcoming Sessions** (the user's wording; `LATER_SHOWN`, then Show All) with Change and Remove, and **+ Add Session** (starts a week after the last one, same time and place); Set Next Session and Add have **Repeat Weekly** (Just This One, or For 2 to `REPEAT_MAX` Weeks: one row a week, `scheduleRows`). Removing the Next Session makes the one after it next. **Double booking** (the user asked): the Set, Change and Add dialogs warn, as the day and times change, when the session overlaps another of the student's or one of their coach's other students' (`watchClash`, `coachBooked`, every Repeat Weekly week checked). A warning, never a block (my choice: two students can share a session), and all in the page, since staff can read every student's sessions. A list, not a calendar like Top Out's (my recommendation, the user agreed: quicker to read for one student on a phone). The student's card lists them under Upcoming Sessions too, and Home's Coming Up shows every session, not one per student. End Coaching clears them (`clear_upcoming_sessions` trigger). Once it has ended (`nextOverdue`), the card turns the warn color with a Needs Update tag and banner, and the Students list tags the student Update Next Session. `training_ended_at` is null while they are being coached; the Coaching Status card on both pages (`trainingCardHTML`, `bindTraining`) has End Coaching (which also clears the next session and the coach, and makes their current plan a past plan in `check_student_coach`, so it works for admins too) and Resume Coaching (plans stay past; the coach picks one to make current). The code and column keep the old "training" names. An inactive student's Sessions card has only Session History, and they have an Inactive tag by their name. The Students list groups them (see Coach ownership), each card with its count; students you can change are tagged Not Invited or Invited until they sign in. The home tile counts your own active students. Inactive students can still sign in and keep their plans, goals and notes.
- `session_history(id, student_id, session_date, start_time, end_time, location, created_at)`: past sessions, unique per student, day and start time. Staff read it, any coach (not about themselves) or admin adds, and the student's coach or an admin changes or deletes (see Coach ownership); a student reads their own. The page logs an ended Next Session (`logEnded`, an upsert that ignores duplicates) just before anyone updates or clears it, including End Coaching. The page does it, not a trigger, because "ended" depends on the local time. Until then `historyOf()` shows the ended next session as the newest past session anyway. Session History, under Next Session in the Sessions card, shows 3 per page (`HISTORY_PAGE`) with a count ("8 sessions since Aug 2026"), + Add Past Session (an `ask()` dialog; `pairTimes`: End Time's `min` follows Start Time, and picking a start fills the end an hour later, or keeps the length when both were set, in this dialog and the Next Session one) and Delete on every row. Deleting an ended Next Session that isn't logged yet clears the next session without logging it. On `#/student/<id>` a row with Coach Notes from that day has a Notes (n) button (`showCoachNotes`: Sessions filter, the page with that day's first note, scrolled to, and every note from that day lit up; `cnoteAt.spot` lights the rest when paging on, until the filter changes or a note is added); a row with none has Add Notes instead (`startCoachNote`: that day becomes the Coach Notes form's filled-in Session Date through `cnoteAt.day`, like picking a missing session, and the Notes box is focused, left as it was). Students see a Your Sessions card on their home page (`studentHistory`), hidden until they have one.
- **Pronouns** (`pronouns` on `staff` and `students`, e.g. `she/her`, empty = not set, at most 40 characters): coaches set a student's on `#/student/<id>`, admins anyone's on `#/user/<id>`, and both Add forms ask. `pronounsField()` is a pick of `PRONOUNS` plus Other with a box to type them; `readPronouns()` reads it back. `pronounsTag()` shows them after the name, smaller and grayed (page headings, Students and Users lists). A student changes only their own pronouns, never their name (so the coach always knows who they are), in the Your Pronouns card at the bottom of their home page, through `update_my_pronouns()`. Text about a person uses `pro(pronouns)`: `p.they`, `p.them`, `p.their` (capitalized `p.They`, `p.Their`) and `p.v(plural, singular)` for the verb, from the first pronoun (she/they → she); anything else, or none, uses they/them.
- `plans(id, student_id, title, overview, start_date, repeats, blocks, active)`: three layouts (`planLayout()`, named by `layoutName()`). `repeats` = Repeat Weekly (the default for new plans): one week of sessions, all week 1, done every week. `false` = Week by Week (week 1, week 2, ... with dates from the start date). `blocks` set (and `repeats` false) = **Training Blocks**: `[{name, weeks}]` in order (name optional, 1 to 52 weeks), each block's sessions done every week of the block, a session's `week` being its block's number; block k starts after the earlier blocks' weeks (`blockStart`, `blockRange`), and `blockNow()` is the block today falls in (migration `2026-09-30-training-blocks.sql`). `active` = current plan. A student has at most one: the `one_current_plan` trigger turns their other current plan into a past plan (a unique index backs it up), and none is allowed. Plan tags (`planTag`): Current, Past, or Inactive for a non-current plan with no start date. New and copied plans are current only if the student has none yet. A student with a current plan sees it straight away.
- `sessions(id, plan_id, week, position, title, details, exercises)`: `exercises` is JSON `[{name, sets, reps, rest, notes, track}]` (`track`: the Training Log fields, see below).
- **Training Log** (`exercise_logs(id, student_id, session_id, exercise_key, exercise_name, logged_on, vals, notes)`, migration `2026-09-30-training-log.sql`, designed on the canvas's Training Log page): students log an exercise from their **current** plan, one summary line per exercise a day (unique student + `exercise_key` + `logged_on`, the student's local day; saving again that day updates it). `exercise_key` is `lower(trim(name))` like `exercises.name_key`, so an exercise's history follows it across plans. `vals` holds the fields its `track` asks for (`LOG_FIELDS`: weight (added, can be below zero, with `unit` lb or kg; lb is the default, the student's pick is kept in `localStorage` `sitstart.unit`), time (seconds), duration (minutes, steps of 5, shown "1 h 30 min" by `fmtMin`, saved as minutes), sets, reps, grade (VB, V0–V17), attempts, problems, edge (mm), board angle (degrees; edge and angle have an Other box, `F.other`, `ls.other`), grip, hand, sent, effort (RPE 1–10, never a trend: harder isn't better)), plus **custom log fields** coaches add. Every field, standard or custom, is a `log_fields(id, key, label, label_key, kind, unit, opts)` row (migrations `2026-10-01-log-fields.sql` and `2026-10-01-standard-log-fields.sql`), managed in the Log Fields card on Exercises & Drills: A to Z, what each asks for, how many exercises use it, Edit and Delete on every one (the user asked; the standard ones are never called "built-in" on the page). The standard nine are `kind 'standard'` rows whose `key` is the field `LOG_STANDARD` works (steppers, lb/kg, grades, edge sizes); the row gives the name, and Grip's choices can be edited. Custom ones are a number with an optional unit (a stepper) or a pick of 2 to 12 choices. Values are kept under the row's `key`, which never changes (nor does `kind`, `sync_log_field`), so renaming keeps the history. Names are unique ignoring case and spaces (`label_key`), and the page checks first (`lfProblem`: a used name, or repeated choices) and shows the error on the field, keeping the Edit dialog open (`ask()`'s `check`). Deleting one takes it off every exercise; plans stop asking for it, old logs stop showing a custom one, and a deleted standard one can't be added back from the page. Everyone signed in reads them: `loadMe` (and the Exercises page) calls `setLogFields`, which rebuilds `LOG_FIELDS` from the rows (all of `LOG_STANDARD` only when the table can't be read) and orders `LOG_KEYS` standard steppers, custom numbers, standard picks, custom picks; Quick Picks leave out deleted fields. `logSummary` adds them at the end, and a custom number is a trend metric after sets. Notes are always there. No body weight anywhere (the user ruled it out). RLS: only the student adds, changes or deletes their own, and only for an exercise in one of their sessions (`my_session_has`); every coach reads them. Coaches never log for students (the user chose this). `track` is set per exercise in Exercises & Drills (`exercises.track`, the default; Log Fields with Quick Picks `LOG_PRESETS`) and copied into a plan's exercise when added or named (`addExercises`, `setExName`); the open exercise in the plan editor has Log Fields with Change (for that plan only) and, once the student has logged it, what they logged last with History; its row says "Last: …". On the student's plan each exercise card (`logAreaHTML`) shows Logged Today with Edit, or "Last time, <day>: …" with **Log**, plus History (n). The Log sheet (design B, the user's pick) has steppers (− value +, the value a typeable box that looks like a field (Grade only steps, so it stays plain); weight steps 2.5 lb or 1.25 kg; time starts at 7s) and chips (edge 6/8/10/12/15/18/20/25/30 mm or Other, grip, sent), starts at last time's values (or the plan's sets, reps and a time like "10s"), shows "+5 lb on last time" in its footer, and Delete Log when editing a day's log. Its **Day** field (today by default, never later) logs a past session: picking a day redraws the sheet for it (`openLogSheet(key, sid, date)`: that day's log to edit, else the last log before it; a new log moved onto a day that has one says so in red under Day, "A log already exists for …", the user asked). **Edit always edits that log** (the user asked: a log made on the wrong day used to be left behind while a second one was made): a sheet opened on a day that has a log is `ls.pinned`, so picking another Day moves the log there (what was typed stays; never onto a day that already has one), and Save updates it by id. History has Edit on every log of an exercise in the current plan. History (`openLogHistory`) shows the best (by `logMetric`: added weight, else grade, time, reps, sets, duration, problems, then custom numbers; never effort) on a dark card with a trend line (`sparkSVG`) and "Up 30 lb since Aug 27", edge chips when several edges were used (it starts on the latest one), then the logs 3 a page (`LOG_PAGE`), Best and New Best tags. The student's home has a Training Log card (hidden until the first log; latest per exercise), and the coach's student page has one with Recent (by day) and By Exercise (with small trend lines) tabs; both open History.
- `goals(id, student_id, body, status, done_at)`: `status` is `current`, `achieved` or `archived`; `done_at` is the day (a `date`, no time) it left `current`. The coach adds, edits, marks achieved (Edit Date changes an achieved goal's day), archives, restores and deletes them on the student page (the Goals card re-renders in place). Students see current goals at the top of their home page and a Goals Achieved card at the bottom; RLS hides archived goals from them.
- Coaches: the `check_student_coach` trigger gives a new student the coach who added them (not themselves), clears the coach and current plan on End Coaching and gives the student back to the coach they had then if that coach resumes (their `student_coaches.ended_at` within 5 minutes of `training_ended_at`), refuses a coach change from anyone but an admin (the SQL Editor can too) and only allows staff with the Coach role. `log_student_coach` keeps `student_coaches(student_id, staff_id, coach_name, started_at, ended_at)`, one row per student and coach: the old coach gets `ended_at`, and a returning coach gets their row back (dates reset), so nobody shows as both current and past. `coach_name` keeps a removed coach's name; `delete_staff()` ends their time as coach and `coach_id` goes to null. The table has RLS and no policies: everyone reads it through `coaches_of(student_id)` (staff, or that student), since students can't read `staff`. Existing students started with no coach.
- `notes(id, session_id, author_id, from_coach, author_name, body, edited_at)`: `author_id` becomes null if the login is deleted (the note stays). Students can add and delete their own. Only the author (student or coach) edits a note (Edit, an `ask()` dialog; "Edited" after the time): the trigger keeps its session, author, side and time and sets `edited_at` when the text changes. Every coach reads them; only the student's coach replies or deletes. A coach's reply shows their name: the `stamp_note_author` trigger writes `author_name` on insert from the poster's own staff row (students can't read `staff`), keeps it (and the rest, see above) fixed on update, and leaves it empty on student notes. The page falls back to "Coach" if it is empty. Plan notes (`notesHTML`) look like text messages: the reader's own notes (`author_id` = the signed-in user) are bubbles on the right, everyone else's on the left.
- `coach_notes(id, student_id, author_id, author_name, session_date, body, created_at, edited_at)`: Coach Notes, private notes a coach keeps on a student. Only staff with the Coach role have a policy (any coach adds; the author or the student's coach edits or deletes; never about yourself); students and admin-only staff can't see them. Typing or picking a listed name fills in its sets, reps, rest and notes (`setExName`). `filledFrom` remembers which name the values came from, so fixing a typo in the name doesn't wipe the coach's own values. The picker also matches purposes (typing one lists its exercises) and shows them under each name (a Find Exercises by Purpose select was tried and removed: the user found typing enough). Purposes only show in the editor: plans never copy them. Save Plan then calls `addToMasterList()`, which adds names not on the list yet with the plan's values (upsert on `name_key`, ignoring ones that exist).

## Conventions

- Colors are tokens on `:root`, with dark mode under `prefers-color-scheme` and `[data-theme]`. Don't hard-code colors.
- Look: muted "moss and bark" colors (moss green accent on warm sand/bark neutrals). Fonts: Bricolage Grotesque for headings (800 for the big student-page ones), DM Sans for body text (the user disliked Inter), Sora for the brand in the header (`CONFIG.siteName` on one line). The header is the page color with a line under it and a filled sand Sign Out. These colors are Sit Start's own; other vsapps apps get their own. The student pages (design D) and the staff pages (Coach & Admin page, design D "Your Picks") were designed on a Claude Design canvas ("Sit Start Student Redesign").
- Logo: a jagged boulder with a deep cave on the left (the overhang you sit start under) and a small crash pad inside the cave, no ring. It is inline SVG in the header (and on the root home page card) using `currentColor`, and `icon.svg` is the favicon (moss, lighter in dark mode). `apple-touch-icon.png` (180px, light mark on moss) is for phone home screens; it and `email-badge.png` are drawn with PowerShell System.Drawing from the same points as the SVG path, so redraw both if the mark changes. `email-badge.png` (96px, moss on transparent, shown at 32px) is the badge in both emails, loaded from the live site since email apps don't show SVG; the emails use the same colors as hex values. The three emails in `supabase/emails/` follow design B on the canvas's Emails page: a big "Hey <first name>," greeting with a moss second line above the card, the same fonts as the student pages (falling back to Arial), and the sender's name signed in moss. They are Sit Start's half of the shared templates: after a change, run `sh supabase-emails/build.sh` and re-paste `supabase-emails/*.html` (Top Out shares the project; see `topout/CLAUDE.md`). Sit Start's `stamp_sender()` sets `topout: false` so an existing login gets Sit Start wording; `login_in_other_app()` (false here, replaced by Top Out's schema) is asked by `gate_signup`, `delete_student`, `delete_staff` and `staff_deactivated` so another app's logins are never blocked, deleted or signed out.
- Must work at phone width (~400px). Students see exercises as cards (`exCardHTML`: name, then Sets / Reps/Time / Rest in three equal centered boxes, "—" when empty, long text wraps inside its box without splitting words that fit (`overflow-wrap: break-word`), then notes); always one card a row, so the order is plain (two a row squeezed the boxes and hid the order). The coach's plan editor keeps its own rows.
- Buttons, headings and labels use title case; hints and messages use sentence case.
- Confirmations use `ask()` (one `<dialog>`), which settles on submit. On a touch screen it focuses the dialog, not its first text box, so the keyboard doesn't pop up (Edit Exercise did). While any modal dialog is open the page behind can't scroll (`html:has(dialog:modal)`).
- Notes (plan notes, Coach Notes, exercise notes, in the editor and the master list) take new lines and **bold**: `rich()` puts a Bold button on a textarea (Ctrl+B too), which wraps the picked words in `**`, and `para()` shows them bold everywhere. `para()` also makes `https://…` and `www.…` clickable links (new tab); `para(s, false)` skips that for text already inside a link (the Students note feed). `textarea[data-grow]` grows to fit its text (CSS `field-sizing`, `growAll()` where it is missing).
